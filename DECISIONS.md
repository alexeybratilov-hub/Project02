# DECISIONS

Журнал архитектурных решений.

## D-000. Документация как часть Definition of Done

- **Статус:** принято.
- **Проблема:** разные ИИ-агенты теряют контекст и переписывают проект.
- **Решение:** документация обновляется на каждом этапе; этап не считается завершённым без неё.
- **Последствия:** больше времени на документы, меньше повторной разработки.

## D-001. Технологический стек

- **Статус:** **принято** (этап 0, 2026-10-22).
- **Проблема:** нужен стек для Windows-портативности, локальной БД, Excel, модульности и серверного развёртывания.
- **Кандидаты:**
  - A: Python + FastAPI + SQLAlchemy/Alembic + SQLite/PostgreSQL + серверные шаблоны + openpyxl;
  - B: Node.js + NestJS + Prisma + SQLite/PostgreSQL + React + exceljs;
  - C: .NET 8 + EF Core + SQLite/PostgreSQL + React или Blazor + ClosedXML.
- **Критерии:** упаковка под Windows, Excel, миграции, скорость разработки с ИИ, серверное развёртывание, поддерживаемость одним человеком.
- **Решение:** вариант A — Python 3.12 + FastAPI + Uvicorn + SQLAlchemy 2.x + Alembic + SQLite (см. D-002) + openpyxl. Клиент — серверные HTML-страницы (Jinja2) с минимальным JavaScript вместо SPA на React/Vite: одна сборка без Node.js, меньше инструментов обслуживанию одним человеком; интерактивность рабочих таблиц достигается серверной пагинацией/фильтрацией.
- **Обоснование:** все библиотеки установлены и проверены в среде разработки (FastAPI 0.116.1, SQLAlchemy 2.1.6, Alembic 1.20.1, openpyxl 3.1.5); импорт/экспорт Excel и миграции работают нативно; упаковывается в портативную папку с embedded Python (D-003); тот же код деплоится на сервер (D-016). Вариант B отклонён: native-модули усложняют портативную упаковку; вариант C отклонён: тяжелее toolchain для одного разработчика с ИИ.
- **Зафиксированные версии зависимостей:** `requirements.txt`.
- **Последствия:** менять стек только при доказанной технической необходимости с записью нового решения в этот журнал.

## D-002. СУБД

- **Статус:** **принято** (этап 0, 2026-10-22).
- **Проблема:** нужна локальная переносимая БД и путь к серверной.
- **Кандидаты:** SQLite (WAL) для локальной версии; PostgreSQL для серверной.
- **Решение:** SQLite в режиме WAL для первой версии; доступ к данным — только через SQLAlchemy ORM, поэтому переход на PostgreSQL возможен без переписывания бизнес-логики (только диалект и конфигурация подключения).
- **Зафиксированные ограничения SQLite:** однопользовательский сценарий записи; при конкурентной записи возможна блокировка базы (busy timeout + явная обработка); целостность связей обеспечивается `PRAGMA foreign_keys=ON` при каждом подключении; файловая БД требует корректного завершения процесса перед копированием.
- **Последствия:** путь миграции на PostgreSQL описан в D-016; резервное копирование — через `sqlite3` backup API, а не копирование файла «на живую» (см. ARCHITECTURE §11).

## D-003. Упаковка под Windows

- **Статус:** **принято** (этап 0, 2026-10-22).
- **Проблема:** запуск из папки не означает отсутствие зависимостей.
- **Кандидаты:** embedded runtime + launcher; single-file executable; portable runtime + .bat; installer.
- **Решение:** портативная папка проекта с встроенным (embedded) Python-рантаймом и файлами запуска `start.bat` / `stop.bat`; приложение стартует на `127.0.0.1` с автоматически открываемым браузером. Installer — позднее, вне первой версии. Single-file executable отклонён: затрудняет обновление кода и миграции, антивирулы часто блокируют такие файлы.
- **Последствия:** структура папки фиксируется на этапе 1 (`runtime/`, `app/`, `data/`, `backups/`, `logs/`); сборка рантайма проверяется вручную на целевой Windows (среза разработки это невозможно — зафиксировано в TESTING как ручная проверка этапа 1).

## D-004. Идентификация записи контингента

- **Статус:** **принято** (этап 0, 2026-10-22).
- **Проблема:** от идентификации зависит связь работников и наследование требований.
- **Кандидаты:**
  - A: юридическое лицо + подразделение + должность + рабочее место;
  - B: A + набор ключевых условий;
  - C: отдельная сущность «рабочее место».
- **Решение:** жёсткого уникального ограничения на комбинацию полей НЕ вводится. Идентификация существующей записи при импорте — по ключу A (юрлицо + подразделение + должность + уточнение рабочего места): если найдена ровно одна запись — она предлагается как кандидат на обновление с показом различий пользователю; если несколько или ноль — импорт требует явного выбора пользователя либо добавляет новую запись с предупреждением. Автоматическая перезапись запрещена (D-010). Путь к варианту C сохраняется через необязательную связь `contingent_records.workplace_id` (миграция при появлении модулей СОУТ/ОПР).
- **Последствия:** индекс (не unique) по `(legal_entity_id, department_id, position_id)`; логика разрешения конфликтов — в сервисе импорта, правила — в IMPORT_EXPORT.md.

## D-005. История переводов работников

- **Статус:** **принято** (этап 0, 2026-10-22).
- **Проблема:** нужно ли хранить историю изменений подразделения/должности/контингента работника.
- **Кандидаты:** без истории в v1; таблица истории; полная версионность карточки.
- **Решение:** таблица `employment_history` (работник, дата начала, подразделение, должность, запись контингента, причина, комментарий). Изменение текущих значений работника создаёт запись истории со старой комбинацией; полная версионность карточки отклонена как избыточная. Дополнительно общий `audit_log` (D-014) фиксирует все изменения.
- **Последствия:** реализация — этап 4; модель данных обновлена (DATA_MODEL §1.13); исторические периоды не перезаписываются.

## D-006. Стратегия обновления и миграций

- **Статус:** **принято** (этап 0, 2026-10-22).
- **Проблема:** обновление не должно ломать данные.
- **Кандидаты:** forward-only миграции + обязательная копия; автоматические миграции при старте; отдельная команда обновления.
- **Решение:** Alembic, forward-only миграции, хранимые в репозитории (`app/alembic/`). Порядок применения: перед применением — обязательная автоматическая резервная копия; в desktop-режиме миграции применяются автоматически при запуске (после создания копии), в серверном — только отдельной командой `python -m app.db upgrade` с подтверждением. Откат миграций не предусмотрен — восстановление через резервную копию.
- **Последствия:** версия схемы попадает в манифест резервной копии; инструкция обновления — README (этап 1+).

## D-012. Тип внутренних идентификаторов

- **Статус:** принято (этап 0, 2026-10-22).
- **Кандидаты:** UUID; целочисленные surrogate-ключи.
- **Решение:** UUID версии 4, хранятся как `CHAR(36)`; генерируются приложением (`uuid.uuid4()`), не СУБД.
- **Обоснование:** переносимость между SQLite и PostgreSQL без изменения кода, устойчивость ссылок при переносе/объединении баз, невозможность угадать идентификатор.
- **Последствия:** чуть больший размер индексов; в интерфейсе идентификаторы не показываются пользователю.

## D-013. Область действия справочника должностей

- **Статус:** принято (этап 0, 2026-10-22).
- **Кандидаты:** глобальный справочник; справочник в рамках юридического лица.
- **Решение:** глобальный справочник `positions` с полем `status`; уникальность названия нормализованного значения (регистр/пробелы). Подразделения остаются в рамках юридического лица.
- **Обоснование:** одна штатная номенклатура у нескольких юрлиц встречается часто; расширение до области юрлица — отдельная миграция при необходимости (поле `legal_entity_id NULL = глобально`).
- **Последствия:** импорт не создаёт должности молча; неизвестное значение показывается пользователю для подтверждения создания (D-010).

## D-016. Путь серверного развёртывания

- **Статус:** принято (этап 0, 2026-10-22).
- **Проблема:** требуется возможность перенести то же приложение на локальный сервер без переписывания бизнес-логики.
- **Решение:** конфигурация через переменные окружения / `config.toml`: `SAOT_DB_URL` (sqlite:///... или postgresql+psycopg://...), `SAOT_HOST` (127.0.0.1 по умолчанию для desktop, 0.0.0.0 только явно), `SAOT_PORT`. Миграции в серверном режиме — только ручной командой (D-006). Авторизация обязательна до включения сетевого доступа — этап за пределами v1, фиксируется в SECURITY.
- **Последствия:** бизнес-логика не должна использовать SQLite-специфичные конструкции сверх ORM.

## D-016. Методика оценки профессиональных рисков (модуль ОПР, этап 7)

- **Статус:** принято по фактической реализации (зафиксировано 2026-10-26 при верификации этапа 7).
- **Проблема:** для модуля ОПР требовалась конкретная методика идентификации и количественной оценки рисков.
- **Решение:** матричный метод 5×5 в соответствии с рекомендациями Приказа Минтруда России № 776н: балл риска = тяжесть последствий (1–5) × вероятность (1–5), диапазон 1–25; уровни: низкий (1–4), умеренный (5–9), высокий (10–15), недопустимый (16–25). Итоговый риск карты определяется по максимальной опасности. Каталог типовых опасностей `DEFAULT_OPR_HAZARDS` (12 шаблонов по категориям 776н) поставляется встроенным; допускается произвольная ручная опасность. План мероприятий — отдельные записи `opr_measures` со статусами «планируется / в работе / выполнено», сроком и ответственным.
- **Последствия:** расширения методики (например, метод Файна-Кинни) добавляются как новый `assessment_method` без изменения существующих карт; нумерация карт уникальна в пределах юридического лица (изолированные дубликаты между юрлицами допустимы).

## D-017. Выбор модуля Этапа 8 — учёт медосмотров (29н/342н)

- **Статус:** принято (2026-10-26).
- **Проблема:** требовалось выбрать следующий прикладной модуль из кандидатов ROADMAP §10: медосмотры (29н/342н), СИЗ, обучение и проверка знаний (Пост. 2464).
- **Решение:** Этап 8 — модуль **«Медосмотры и психиатрическое освидетельствование»** (ID `medical`).
- **Обоснование:** 
  1. Непосредственная логическая связь с уже реализованным контингентом (поля 29н/342н заложены на Этапе 3);
  2. Модуль ОПР (Этап 7) использует те же сущности (juridical entities, contingent records) — единая база для планирования медосмотров по вредным факторам;
  3. Требование законодательства: обязательность предварительных и периодических медосмотров для занятых на работах с вредными условиями (ст. 213–218 ТК РФ, Приказ Минздрава 29н/342н);
  4. Простота модели данных относительно СИЗ (нет норм ЕТН и сроков носки) и обучения (нет протоколов и удостоверений).
- **Последствия:** 
  - Сущности: `medical_examination_cards` (карты медосмотров), `medical_appointments` (предварительные записи), `psychiatric_examinations` (акты психиатрического освидетельствования);
  - Зависимости: ядро, юридические лица, контингент, работники;
  - Интеграция с СОУТ: автоматическое формирование плана медосмотров по классам условий труда и вредным факторам;
  - Импорт/экспорт Excel по шаблону STAGE_6_MODULES_TEMPLATE.

## D-018. Модуль Этапа 9 — учёт средств индивидуальной защиты (Приказы 766н и 767н ЕТН)

- **Статус:** принято (2026-10-26).
- **Проблема:** требовалось реализовать модуль учёта бесплатной выдачи работникам специальной одежды, специальной обуви и других средств индивидуальной защиты (СИЗ), а также смывающих средств в строгом соответствии с актуальным российским законодательством.
- **Решение:** модуль **«Средства индивидуальной защиты (СИЗ)»** (ID `ppe`), основанный на действующих нормативных правовых актах:
  1. **Приказ Минтруда России от 29.10.2021 № 766н** («Правила обеспечения работников средствами индивидуальной защиты и смывающими средствами»). Формат личной карточки учёта выдачи СИЗ соответствует Приложению № 2 к Приказу № 766н (антропометрические параметры: рост, размеры одежды, обуви, головного убора, противогаза/респиратора, перчаток).
  2. **Приказ Минтруда России от 29.10.2021 № 767н** («Единые типовые нормы выдачи СИЗ и смывающих средств» — ЕТН). Нормы выдачи СИЗ (`ppe_norms`) привязываются к профессии/должности (справочник `positions`) и подразделению, содержат пункт ЕТН/ЛНА, периодичность носки в месяцах (0 — «до износа»), количество и признак дежурного СИЗ.
  3. **Учёт выдачи и возврата (`ppe_issuances`):** каждая запись фиксирует выданное СИЗ, количество, дату выдачи, плановый срок возврата (`due_return_date = issue_date + wear_period_months`), номер документа/электронной подписи, а также факт сдачи/списания с указанием причины (износ, увольнение, непригодность/порча, перевод) по ст. 221 ТК РФ.
- **Ограничения и правила целостности:**
  - У одного работника может быть только одна активная личная карточка СИЗ в пределах организации (Приказ 766н).
  - Номер карточки уникален в пределах юридического лица (изолированные дубликаты между организациями допускаются).
  - Контроль сроков: автоматическое выявление просроченных к замене СИЗ (`has_overdue` / `overdue`).
  - Резервное копирование и аудит охватывают все операции с нормами, карточками и выдачами СИЗ.
- **Последствия:**
  - Сущности: `ppe_norms` (нормы выдачи), `ppe_cards` (личные карточки), `ppe_issuances` (фактические выдачи/возвраты);
  - Зависимости: ядро, юридические лица, контингент, работники, справочник должностей;
  - Шаблоны Excel: `template_ppe_norms.xlsx` и `template_ppe_cards.xlsx` с генерацией предпросмотра и защитой от дублирования.
