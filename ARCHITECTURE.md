# ARCHITECTURE

## 1. Статус документа

Документ описывает **утверждённую целевую архитектуру этапа 0** (2026-10-22). Код приложения ещё не реализован; после этапа 1 документ приводится в соответствие с фактическим кодом. Стек утверждён в D-001, СУБД — D-002, упаковка — D-003.

## 2. Принципы

- модульный монолит, а не микросервисы;
- единое хранилище данных;
- единая модель данных и справочники;
- явные миграции;
- транзакционность критических операций;
- архивирование вместо каскадного удаления;
- журналирование значимых действий;
- отсутствие обязательного облака;
- переносимость под Windows;
- возможность последующего серверного развёртывания;
- документация как часть Definition of Done.

## 3. Логическая архитектура

```text
Браузер (SPA, русский интерфейс)
        |
        | HTTP API
        v
Серверное приложение (один процесс)
├── Ядро
│   ├── реестр модулей
│   ├── навигация и меню
│   ├── авторизация (позднее)
│   ├── аудит
│   ├── импорт/экспорт
│   ├── резервное копирование
│   ├── настройки
│   ├── обработка ошибок
│   └── журналирование
├── Доменные модули
│   ├── юридические лица
│   ├── контингент
│   ├── работники
│   └── будущие модули
├── Слой доступа к данным
└── Хранилище
    ├── реляционная БД
    ├── папка attachments
    ├── папка backups
    └── папка logs
```

Клиент не обращается к базе напрямую. Все операции — через API.

## 4. Контракт модуля

Модуль описывает:

- `id`, `name`, `version`;
- зависимости от других модулей;
- миграции;
- маршруты API;
- пункты меню и маршруты клиента;
- права доступа (в перспективе);
- обработчики импорта и экспорта;
- виджеты главной страницы;
- настройки.

Реестр модулей загружает включённые модули. Отключение модуля скрывает его маршруты и меню, но не удаляет данные. Ядро не должно зависеть от необязательных модулей.

## 5. Жизненный цикл модуля

1. Регистрация в реестре.
2. Проверка зависимостей.
3. Применение миграций модуля.
4. Публикация маршрутов и меню.
5. Работа.
6. Отключение без удаления данных.
7. Повторное включение.

## 6. Доступ к данным и транзакции

- параметризованные запросы или ORM;
- запрет конкатенации SQL;
- транзакции для импорта и многошаговых операций;
- серверная пагинация, фильтрация и сортировка;
- индексы по внешним ключам и поисковым полям;
- бизнес-проверки ссылочной целостности на уровне сервисов.

## 7. Обработка ошибок

- типизированные доменные ошибки;
- ошибки валидации с привязкой к полям;
- понятные сообщения на русском языке;
- без стек-трейсов в интерфейсе;
- корреляционный идентификатор для поиска в логах.

## 8. Журналирование и аудит

Два уровня:

- технический лог приложения;
- бизнес-журнал аудита.

Аудит фиксирует создание, изменение, архивирование, восстановление и импорт. Снимки до/после хранятся в JSON. JSON используется только для аудита, а не вместо основной структуры данных.

## 9. Файловое хранилище

Структура:

```text
/attachments/<entity_type>/<entity_id>/<uuid>_<filename>
```

Правила:

- проверка размера и типа;
- запрет исполнения загруженных файлов;
- контрольная сумма;
- отсутствие доступа по произвольному пути.

## 10. Импорт и экспорт

Конвейер: шаблон → загрузка → проверка структуры → предпросмотр → ошибки/предупреждения/дубликаты → подтверждение → транзакция → отчёт.

Детали — `IMPORT_EXPORT.md`.

## 11. Резервное копирование

Копия включает:

- дамп базы или консистентную копию файла БД;
- папку attachments;
- манифест с версией схемы, датой, контрольными суммами.

Восстановление:

- предупреждение о последствиях;
- обязательная предварительная копия текущего состояния;
- проверка целостности после восстановления.

## 12. Миграции

- Alembic (D-006), forward-only, каталог `app/alembic/`;
- таблица `alembic_version` — каноническая версия схемы;
- перед применением — обязательная автоматическая резервная копия;
- desktop-режим: миграции применяются автоматически при запуске; серверный режим: отдельной командой с подтверждением;
- откат не предусмотрен — восстановление из резервной копии;
- запрет ручного редактирования рабочей базы.

## 13. Развёртывание

### Локальное Windows (D-003)

Портативная папка проекта:

```text
<SАОТ>/
├── runtime/     — embedded Python 3.12 + site-packages
├── app/         — код приложения (FastAPI, шаблоны, alembic)
├── data/        — saot.db (SQLite WAL)
├── attachments/ — связанные файлы
├── backups/     — резервные копии
├── logs/        — технические логи
├── start.bat    — запуск (запуск без установки, открывает браузер)
└── stop.bat     — остановка
```

### Серверное (D-016)

Тот же код; `SAOT_DB_URL` → PostgreSQL; `SAOT_HOST=0.0.0.0` только явно и только после включения авторизации; миграции — ручной командой.
